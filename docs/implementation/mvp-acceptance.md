# Waves 1–2 MVP acceptance evidence

**Status, 2026-11-11:** The end-to-end MVP gate in [product spec #2](https://github.com/fnayou/pify/issues/2) remains open. Pify is a bootstrap project with a private development package, no supported release, and no public install command. Closed implementation issues, green CI checks, and one owner-run hosted-model check prove the slices below, not a complete new-user or existing-user journey.

The automated evidence uses official Pi 1.4.0 with isolated agent directories and workspaces on macOS and Linux. Tests do not touch an active Pi installation. “Fixture” means a local simulated service or temporary Pi setup; it does not prove a hosted provider account works.

## Integrated pinned Git candidate

The isolated [Git package smoke](../../scripts/smoke_pi_git_package.py) now runs a joined journey on macOS and Linux. A fresh agent previews a reviewed clone, installs and verifies the pinned package, checks skills and health without optional model or project integration files, starts an ordinary TUI, records and rolls back the Pify theme, checks a later session, and removes the package. An existing agent preserves a user skill and unrelated package, uses local and LiteLLM-compatible loopback models after the local endpoint stops, checks Safe/Balanced/Full headless outcomes, retries a failed same-pin update, and removes Pify without changing its post-startup settings or user files. Pi's TUI may add its own `lastChangelogVersion` setting; the preservation comparison starts after that native startup. These fixtures do not prove a live hosted call, GitHub origin, or a supported public installation.

The [synthetic Git version smoke](../../scripts/smoke_pi_git_version_change.py) makes a throwaway next-patch commit in a temporary mirror. It proves a successful native A→B→A transition and that an npm failure after checkout reset can leave B files with the A declaration. Pi leaves an incomplete-update marker and `/pify-health` reports `unknown`. A private mirror made from the installed A checkout before the change passes Git integrity checks; an empty mirror blocks the update attempt. With the original source unavailable, Pi reinstalls A from that backup through a command-scoped local URL rewrite. This proves an offline recovery path under Pi 1.4.0, not an atomic update, a release backup policy, or a supported user procedure. No synthetic commit or package is published.

## Gate closure

Close [MVP gate #81](https://github.com/fnayou/pify/issues/81) only when one recorded acceptance run covers fresh and existing isolated Pi setups through a supported user entrypoint: preview and approval, install/adopt, read-only health, local and hosted-cloud model selection, headless refusal, failed-change recovery, rollback, uninstall, and preservation of unrelated state. Run the applicable automated path on macOS and Linux; record any platform-specific live-provider evidence separately. Keep the release blocked until every MVP row has evidence.

The corrected `YYYY.M.PATCH` validator and owner-controlled `@fnayou/pify` private package name are prerequisites, not release proof. [Release policy #55](https://github.com/fnayou/pify/issues/55) still needs authoritative version-history checks and a separately approved publication path. No release, package publication, or active-user migration is part of this acceptance document.
