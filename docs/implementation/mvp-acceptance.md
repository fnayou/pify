# Waves 1–2 MVP acceptance evidence

**Status, 2026-11-05:** The end-to-end MVP gate in [product spec #2](https://github.com/fnayou/pify/issues/2) remains open. Pify is a bootstrap project with a private development package, no supported release, and no public install command. Closed implementation issues and green CI checks prove the slices below, not a complete new-user or existing-user journey.

The automated evidence uses official Pi 1.4.0 with isolated agent directories and workspaces on macOS and Linux. Tests do not touch an active Pi installation. “Fixture” means a local simulated service or temporary Pi setup; it does not prove a hosted provider account works.

| MVP gate | Evidence now | Remaining acceptance gap |
| --- | --- | --- |
| Fresh install and ordinary Pi session | [`smoke_pi_package.py`](../../scripts/smoke_pi_package.py) installs this repository by local path, checks `pi list`, starts RPC and TUI sessions, verifies package resources, then removes the package and confirms its commands disappear while an existing user skill remains. CI runs this on macOS and Linux. | Provide a supported, documented user setup path for the first usable distribution. A local development fixture is not a released installer. |
| Existing Pi adoption, backup, rollback, and uninstall | [`adoption.test.mjs`](../../tests/adoption.test.mjs) and [`managed-state.test.mjs`](../../tests/managed-state.test.mjs) cover read-only preview, exact conflict approval, scoped backup, failed apply rollback, drift, and preservation of unrelated files. The package smoke covers native Pi removal with an existing user skill. | [`adoption.md`](adoption.md) documents a module API, not a command usable in ordinary Pi sessions. Exercise preview, approval, apply, failed update recovery, rollback, and uninstall through the supported user entrypoint on both platforms. |

## Gate closure

Close [MVP gate #81](https://github.com/fnayou/pify/issues/81) only when one recorded acceptance run covers fresh and existing isolated Pi setups through a supported user entrypoint: preview and approval, install/adopt, read-only health, local and hosted-cloud model selection, headless refusal, failed-change recovery, rollback, uninstall, and preservation of unrelated state. Run the applicable automated path on macOS and Linux; record any platform-specific live-provider evidence separately. Keep the release blocked until every MVP row has evidence.

The corrected `YYYY.M.PATCH` validator and owner-controlled `@fnayou/pify` private package name are prerequisites, not release proof. [Release policy #55](https://github.com/fnayou/pify/issues/55) still needs authoritative version-history checks and a separately approved publication path. No release, package publication, or active-user migration is part of this acceptance document.
