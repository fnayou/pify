# Read-only health report

Pify remains a bootstrap project. When its Pi extension is loaded, `/pify-health` reports the observed Pi version against the tested 1.4.0 target, whether Pi settings declare this Pify package, the detected local or npm source kind, the private package metadata version, bundled skills and their pinned source revisions, the saved theme and whether Pify rollback is available, this project's opt-in workflow state, and resources with valid Pify provenance. RPC clients receive JSON; the Pi terminal shows a short text report.

The command reads Pi settings, the package's skill catalog, Pify's ownership and theme journals, and the current project's workflow skill. It does not create a manifest, change settings, probe a model endpoint, or require optional services. A missing setup reports `not_installed` with an empty inventory and `themeSelection.status: not_configured`. An unreadable settings file or ownership manifest reports `unknown` or `unavailable` with a warning. Damaged or unsafe theme state reports `themeSelection.status: unavailable` and never claims rollback is safe; its warning does not include file contents. A modified managed file appears under `conflicts`, not under `managed`. Files absent from valid Pify provenance are never listed as managed. Bundled skills are package resources, not files managed through the ownership manifest. Pi may suppress a bundled skill when another skill has the same name; `/pify-health` lists package contents, not the active Pi command winner.

The project workflow state comes from the exact `.pi/skills/pify-development-workflow/SKILL.md` file in the current working directory. It reports `enabled` only when that file matches Pify's template, `disabled` when absent, and `conflict` when a different file occupies the path. Health does not claim ownership of an existing matching file. Pi loads project skills only after project trust is granted.

For a personal npm source, health reports `installed` only when settings contain one exact pinned `npm:@fnayou/pify@VERSION` declaration, the loaded package manifest has that name and version, and the loaded root is Pi 1.4.0's managed npm path under the agent directory. String and object declarations are supported. An unpinned, conflicting, or path-mismatched Pify npm declaration reports `unknown`; unrelated package names report `not_installed`. This confirms local declaration and loaded-path consistency, not registry or tarball provenance. The package remains private and unpublished. Git sources, project-local packages, and legacy global npm paths are not verified here. See [Pi 1.4.0's package contract](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/packages.md).

Each new managed record stores the private package version present when the change was prepared. Older records without a version report `null`; the command does not guess. The package metadata version is not a release announcement. Pi versions other than the pinned 1.4.0 target are `unverified`, not declared incompatible.
