# Proposed native Pi setup lifecycle

**Status:** The design from [#89](https://github.com/fnayou/pify/issues/89) has private local and pinned-Git source review slices. The [MVP gate #81](https://github.com/fnayou/pify/issues/81) remains open. Pify is a bootstrap project; this is not a supported installation guide or a release claim.

## Ownership and entrypoints

Pi owns package registration and resource loading. Its documented commands are `pi install <source>`, `pi list`, `pi config`, and `pi remove <source>`. A local package loads from its path without copying its resources. A pinned npm version requires a reviewed registry publication; a pinned Git commit requires a reviewed, reachable repository. The current private package declares one extension, two skills, and one theme; it declares no prompt templates. See the pinned [Pi 1.4.0 package](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/packages.md) and [CLI](https://github.com/earendil-works/pi/blob/v1.4.0/packages/coding-agent/docs/cli.md) contracts.

Pify owns only side effects performed by its extension after Pi loads it. Current examples are theme selection in agent settings and an opt-in project workflow file. The regular-file adoption module has no selected package resource to copy into the agent directory. Package resources must stay in Pi's package loader; copying them solely to use the adoption module would create duplicate ownership and a second removal path.

The private local-package preflight uses `/pify-setup preview` in a transient Pi session started with `pi -e <local-package-path> --pify-preflight`. Pi documents `-e` as loading a package for one invocation without adding it to settings. The flag suppresses Pify's fresh-theme selection for this preview session only. The command reports the loaded package directory, a digest of its manifest and declared resources, a bounded runtime-source digest, a path-bound review code, current agent-level resource collisions, the planned Pi package declaration, and the first-session theme outcome. The runtime digest covers `package.json` and files under `extensions/`, `src/`, `skills/`, `themes/`, `templates/`, and `prompts/` when present. It rejects linked or oversized content. It marks resource precedence, project resources, and npm/git origin as unverified. It does not call `pi install`, write Pify state, or ask for credentials. Transient Pi startup itself may initialize Pi-owned files; this is a Pify no-write promise, not a whole-process no-write promise. Running an extension executes its code, so the source must be reviewed before preflight.

For a reviewed clone at a detached full commit, `/pify-setup preview-git <commit>` uses the same transient `pi -e <clone> --pify-preflight` entrypoint. It requires `.git/HEAD` to contain the requested commit and reports a distinct review code derived from that commit and the bounded runtime digest. The code does not depend on the clone's local path. It reports existing Pify Git declarations as already present or conflicting, but does not install or approve a replacement. After a native `pi install git:github.com/fnayou/pify@<commit>`, an ordinary session can run `/pify-setup verify-git <commit> <review-code>`. Verification requires the exact Pi-managed Git declaration, checkout identity, and reviewed runtime bytes; a loadable changed runtime file or mismatched commit reports `mismatch`. A broken extension may prevent the command from loading at all. `/pify-health` remains the separate read-only install inventory. Neither command attests GitHub origin, worktree cleanliness, external dependencies, or files outside the bounded runtime roots. Both commands run only after Pi has loaded extension code, so the source must be reviewed before either invocation.

The proposed next step is for the user to run `pi install <same-reviewed-source>`, start an ordinary Pi session, run `/pify-setup verify <review-code>`, and run `/pify-health`. Verification reads the current local package path and runtime files and checks Pi's package declaration. A changed path or runtime file yields a mismatch; a missing declaration yields `not_installed`. It writes no Pify state. A changed source requires a new preview. This is post-install evidence: Pi loads the extension before the verify command runs, so the check cannot prevent changed code from executing. It does not attest git/npm origin, files outside the named runtime roots, or external dependencies. `pi install` changes Pi's package declaration outside Pify's permission gate. Pify does not claim to approve or roll back Pi's internal package operation. [Issue #30](https://github.com/fnayou/pify/issues/30) requires the first ordinary interactive session to select the Pify theme when Pi has no saved theme. A user who declines that default must make an explicit `system` or personal theme choice through Pi before the first installed session. On an existing Pi setup, a same-name user skill must remain untouched and retain the observed Pi precedence; no Pify file adoption is needed for that collision.

## Optional changes and removal

After installation, any optional Pify-managed change needs a fresh exact preview and explicit choice. `/pify-theme status` and `/pify-theme enable` cover a later saved theme choice in a terminal. Both an explicitly enabled theme and the approved fresh-theme default have a journaled rollback through `/pify-theme rollback`; a later personal theme change blocks rollback and remains untouched. `/pify-workflow enable` is a separate project opt-in, not part of personal package setup. The generic file-adoption module remains internal until a real resource and user need justify its interface.

If a Pify-managed change fails, the ordinary session must report the failed target and recovery state. The user checks `/pify-health` and the relevant status command, then retries rollback only when the recorded digest or prior theme still matches. The isolated package smoke forces a theme write failure after its private journal is prepared in a live Pi RPC session. It checks the conflict response, unchanged prior setting, `/pify-health` and `/pify-theme status` recovery results, and scoped rollback before native removal on macOS and Linux. Health reads the saved theme and rollback availability from that journal without changing it. This proves theme recovery only. A drifted file or theme remains in place with a conflict result for manual review. The current package has no regular-file adoption target and therefore no file conflict approval to request; a future target must use the existing exact-path preview and approval rules before it is added to this lifecycle. If native `pi install` fails, inspect `pi list` and Pi's own error before retrying; Pify cannot claim transactional recovery for Pi's package manager.

Uninstall order is: inspect `/pify-health` and `/pify-theme status`; roll back a journaled theme selection if desired; exit Pi; run `pi remove <same-source>`; then verify `pi list` and the unrelated Pi state. The package extension is unavailable after removal, so theme rollback must happen first. Pify's private recovery journal and backups are retained for inspection. A drifted file or theme is preserved and reported for manual review, never overwritten to force a clean status.

Headless Pify commands must return the existing structured `clarification_required`, `approval_required`, or `denied` result when exact scope or approval is missing. They must not prompt or mutate. Pi's own `install`, `remove`, and `update` commands remain outside that gate. A disposable same-pin update test checks fetch-failure preservation and retry. A separate two-commit fixture checks A→B→A through native `pi install`. When npm fails after Pi resets the checkout to B, the settings declaration can still point to A; `/pify-health` reports `unknown` and Pi leaves an incomplete-update marker. A Git backup made before the change lets Pi reinstall the recorded A pin even when the original source is unavailable. These are test findings, not an approved user update procedure. Automatic package updates and a backed-up release update/rollback procedure remain [#55](https://github.com/fnayou/pify/issues/55) work.

### Candidate offline rollback sequence (disposable fixture)

The [version-change smoke](../../scripts/smoke_pi_git_version_change.py) runs this order with a temporary Pi agent directory and a private backup under a mode-0700 temporary parent:

1. Record the installed A source, full commit, review code, and healthy `installed (git)` result. Check that the Pi declaration and managed checkout both match A.
2. Create a bare local Git backup. Push the installed checkout's A commit to `refs/heads/pify-backup`. Verify the ref resolves to A and `git fsck --strict --no-reflogs` passes. Stop before changing versions if the backup is empty or invalid. The backup contains Git objects from the managed checkout, not unrelated Pi settings, credentials, or sessions.
3. Preview the reviewed B checkout. Run native `pi install git:github.com/fnayou/pify@<B>`. After success, verify the B declaration, checkout, runtime review code, and health. If it fails, inspect `/pify-health` and the incomplete-update marker before further action.
4. To restore A when the source is unavailable, run `pi install git:github.com/fnayou/pify@<A>` with Git's `url.<file-URL-to-private-backup>.insteadOf=https://github.com/fnayou/pify` supplied only to that command. Then verify the exact A declaration, checkout, runtime review code, and health; confirm the incomplete-update marker is gone. The rewrite is an environment setting for one invocation, not a persistent Git configuration change.

This is a fixture-proven candidate, not an installation or release instruction. It covers the observed post-checkout npm failure in Pi 1.4.0. It does not cover a corrupted Pi settings file, a damaged backup, an unreviewed source, or every Pi failure phase. A user procedure still needs private backup location and retention choices, an approved release source, and evidence through the full supported setup journey.

## Gaps before this can be supported

- The local preflight reports declared resources, runtime files, and agent-level collisions. Post-install verification compares the local path, runtime content, and Pi declaration. The Git preview and verification compare a reviewed clone with the separate managed checkout using a commit-bound runtime review code. Neither path verifies project precedence, arbitrary repository files, remote origin, or unchanged source before Pi loads it. Isolated Pi 1.4.0 smokes exercise both paths on macOS and Linux.
- First ordinary interactive startup selects the Pify theme when no theme key exists; the preflight flag suppresses this only in the transient preview. The isolated fresh fixture now checks the private rollback record, restored `system` choice, another ordinary session, and native removal. The supported distribution journey remains unproved.
- `/pify-health` recognizes local declarations and checks exact pinned personal npm declarations against the loaded package name, version, and Pi-managed npm path. The npm evidence uses synthetic settings; no package has been published or installed from a registry. For `git:github.com/fnayou/pify@COMMIT`, health also checks an exact full commit pin, managed Git path, package name, and detached `HEAD`. A cross-platform isolated smoke installs and removes this source through Pi using a temporary Git mirror of the checked-out commit. A separate optional smoke fetched merged commit `af6d0354a4f07a98c76fafcd6642984990a531ec` from the public GitHub URL and completed preview, install, verification, health, TUI startup, and removal on macOS with Pi 1.4.0. That run checked the live transport and local checkout consistency; it does not add signed source provenance, attest worktree integrity, or prove Linux's live GitHub path. Project-local sources remain unverified.
- No supported published source or user setup guide exists. Synthetic version changes prove offline recovery from a scoped Git commit backup in a fixture, but do not supply an approved user backup policy, release review, or supported update procedure. Keep the first usable release blocked by #81 and #55.

The local preflight is development evidence, not permission to install Pify into an active Pi setup.

## Acceptance plan

Use official Pi 1.4.0 in separate fresh and existing temporary agent directories and workspaces on macOS and Linux. Do not use an active Pi installation. Record the source, Pi version, platform, and redacted results.

1. Snapshot the existing fixture, including an unrelated Pi package, same-name user skill, personal theme, credentials, sessions, and project files. Run transient preflight and verify the Pify-owned portion is unchanged. Compare the path-bound review code with the declared local package in an ordinary session after `pi install`.
2. Install the same source through Pi. Start ordinary TUI and RPC sessions. Check `pi list`, `/pify-health`, resource precedence, no duplicate package resources, and preservation of unrelated state. The fresh fixture must show the theme plan before install, then apply the approved #30 default and offer rollback. A fixture with explicit `system` or personal theme must retain that choice.
3. Exercise optional theme approval and rollback, a denied headless request with no exact scope, and a forced failure after the theme journal is prepared. The isolated package smoke now proves the ordinary-session error and recovery path. Preserve a later user theme edit; if a real regular-file adoption resource is introduced, add its preview, exact conflict approval, failed apply, rollback, and uninstall to this same journey.
4. Remove Pify through Pi after Pify-managed rollback. Verify no unrelated package, skill, setting, credential, session, or project file changed. Record any Pi-owned files that Pi itself creates or retains.

The isolated local package smoke combines path-bound source verification, local and LiteLLM-compatible loopback model paths, headless permission refusals, health, successful and failed theme recovery, and native removal in one existing-user fixture. A separate fresh fixture covers preflight, install, source verification, ordinary health and TUI startup, journaled theme rollback, another session, and removal. The Git package smoke joins commit-bound preview and verification with ordinary TUI theme recovery, local and LiteLLM-compatible loopback model selection, Safe/Balanced/Full headless outcomes, same-pin update recovery, and removal in fresh and existing fixtures. The fresh fixture works without a model configuration, agent RTK hook, or project integration file. A separate synthetic two-commit smoke checks version-change recovery from a private local Git backup without publishing an artifact. A supported distribution entrypoint, backed-up user update procedure, and live hosted evidence within the full setup journey remain for #81. One owner-run hosted result on macOS is already recorded there; it does not prove the full setup journey.
