## Pi lifecycle and dashboard feed

Pi v1.4.0 extensions expose `agent_start` / `agent_end`, turn and message events, tool start/update/end, `tool_result`, `agent_before_settle` / `agent_settled`, and session start/shutdown. `agent_end` is not final-idle: retries, compaction recovery, or queued input may start another run. `agent_settled` marks that automatic continuation has stopped. [Pinned extension lifecycle docs](https://raw.githubusercontent.com/earendil-works/pi/v1.4.0/packages/coding-agent/docs/extensions.md)

| Feed fact | Pi source event/API | Dashboard use and gap |
|---|---|---|
| Parent input/run state | `input`, `before_agent_start`, `agent_start`, `agent_end`, `agent_settled` | Show accepted input, active run, retry/continuation, and settled state. Use `agent_settled` for final idle. |
| Parent turn/model activity | `turn_start`, `turn_end`, `message_start/update/end`, provider response/stream events | Show current turn and assistant progress. Provider stage availability depends on transport. |
| Tool activity | `tool_execution_start/update/end`, `tool_call`, `tool_result` | Show active tool, update text and result state. Tool error result content needs explicit normalization. |
| Child status | No generic parent lifecycle event for arbitrary subagents | **Instrumentation required:** launcher emits child id, name, parent, queued/running/terminal state, timestamps, and status transitions. Pi example parses child JSON output itself. Nested tool calls expose status, duration and error, but omit results and may be incomplete. [Nested-call contract](https://raw.githubusercontent.com/earendil-works/pi/v1.4.0/packages/coding-agent/docs/extensions.md) |
| Cancellation | Tool/run `AbortSignal` and child process outcome are available at relevant extension boundaries | **Instrumentation required:** propagate cancellation, distinguish user cancel, timeout, child abort, and parent shutdown; retain terminal state and partial output. Pi's example kills child process on abort. |
| Elapsed time | No general elapsed-duration event contract for every run or child | **Instrumentation required:** store monotonic start/end timestamps in the adapter; derive elapsed duration. |
| Errors and results | Tool result/error and child JSON output can carry detail | **Instrumentation required:** normalize launch/parse/exit errors and preserve result references. Do not infer success from process exit alone. |
| Usage/context | Assistant messages carry provider usage; context usage and session entries are queryable | Snapshot child and parent usage separately, retain model and context token values, and label estimates versus provider-reported totals. |

Proposed status-feed record: `eventId`, `parentSessionId`, `runId`, optional `childId`, `timestamp`, `phase`, `status`, optional `tool`, `elapsedMs`, `usage`, `contextTokens`, `error`, and `resultRef`. Keep detailed result bytes outside the dashboard view; display a stable summary plus a route to inspect the original. **This schema and all instrumentation are proposed, not verified against a Pify implementation.**

## Optional footer adapter boundary

Pi v1.4.0 documents `ctx.ui.setStatus(key, text)` as status text in the footer/status bar. Its extension API also exposes `ctx.ui.setFooter(factory | undefined)`; that call replaces the footer, while `undefined` restores Pi's built-in footer. The API documents no getter or ownership check for a user-installed footer. [Pinned extension types](https://raw.githubusercontent.com/earendil-works/pi/v1.4.0/packages/coding-agent/src/core/extensions/types.ts)

Proposed adapter: consume the dashboard's read-only status feed and publish one namespaced status contribution through `setStatus("pify", text)`. Do not call `setFooter`, edit extension files, or patch user config. Keep the adapter separate and opt-in. It should render only in TUI mode and remove its own namespaced status at shutdown. A user with a custom footer must opt into explicit composition in that footer; Pify cannot safely detect or replace it. Validate against Pi v1.4.0 and custom-footer ownership before implementation. No adapter compatibility has been tested.

## Recommendation / next decision

Proceed to design against Pi's pinned v1.4.0 extension API and official subagent example, with caller-bounded child authority and a separately instrumented status feed. Treat Pi's example as a starting point requiring security and behavior review. Do not select `badlogic/pi-subagent` until dated maintenance and a licence are established. Keep footer integration to an opt-in `setStatus` adapter; never take ownership through `setFooter`.

For optimization, evaluate RTK `rtk-oss` and Caveman Engine as separate candidates. Neither is compatible merely because it documents Pi support. Require pinned version, license review, command/output fidelity evidence, and recovery tests first. Keep Caveman response style separate from context compression. For Caveman, current licensing documentation says Apache-2.0 from v3.0.0 onward; pin the release and verify package artifacts before adoption.

**Uncertainty:** No candidate was installed or executed. No compatibility or fidelity tests were run. All Pify behavior remains proposed.
