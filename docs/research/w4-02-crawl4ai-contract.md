# W4-02-D: optional Crawl4AI page retrieval contract

**Status, 2026-11-14:** Discovery for [#146](https://github.com/fnayou/pify/issues/146), supporting [research capability #38](https://github.com/fnayou/pify/issues/38). Pify remains a bootstrap project. This is a proposal, not an implemented integration or a claim about the owner's private service. No instance, endpoint, token, or page response was contacted or recorded.

## Decision

**Conditional go for a narrow `POST /crawl` REST adapter in #147; no go for exposing the whole Crawl4AI MCP tool set.** The initial compatibility target is **exactly Crawl4AI Docker server v0.9.5**, not `latest` or an untested range. Its [release](https://github.com/unclecode/crawl4ai/releases/tag/v0.9.5) and [changelog](https://github.com/unclecode/crawl4ai/blob/v0.9.5/CHANGELOG.md) identify it as the 2026-10-14 security release. The pinned [security policy](https://github.com/unclecode/crawl4ai/blob/v0.9.5/SECURITY.md) supports 0.9.x only and says older lines receive no backports. Later patch versions need fresh advisory and contract review. A version string or healthy `/health` response is necessary evidence, never proof of egress safety; the operator must verify the deployed image and its network policy.

The upstream [license at v0.9.5](https://github.com/unclecode/crawl4ai/blob/v0.9.5/LICENSE) is Apache-2.0. Pify would send bounded requests to a separately operated service; it would not package or manage Crawl4AI. Firecrawl stays optional and absent, as [#38](https://github.com/fnayou/pify/issues/38) specifies. The older [W0-05 survey](w0-05-skill-survey.md) did not test either service.

| Responsibility | Boundary for #38 and #147 | Evidence |
| --- | --- | --- |
| Web search and URL discovery | A separate, configurable source may supply candidate URLs later. A user-supplied URL must work without search. Crawl4AI domain/link seeding is not evidence of general web search. | The self-hosted [API lists crawl and extraction endpoints](https://docs.crawl4ai.com/core/self-hosting/), not a general search contract; this is an inference from the documented surface. |
| Page retrieval and extraction | #147 may fetch one supplied public URL and return bounded page text with provenance. No deep crawl, LLM extraction, hooks, JavaScript, screenshots, PDF, jobs, or webhooks. | The [server routes](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py) expose `POST /crawl` separately from these powers. |
| Research synthesis | #38 must decide claims, citations, uncertainty, budgets, and off switch. Page text is untrusted data and never instructions for Pi or Pify. | [#38 acceptance criteria](https://github.com/fnayou/pify/issues/38). |

## Transport choice

| Option | Verified fit | Decision |
| --- | --- | --- |
| Pi extension + REST | The existing Pify package uses Pi extensions. Crawl4AI v0.9.5 [exposes authenticated `POST /crawl`](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py); its [self-hosting guide](https://docs.crawl4ai.com/core/self-hosting/) documents Bearer-token setup. The server also has other public routes, so deployment access controls remain necessary. An extension can expose only the bounded page-result operation. | Select for a fixture-tested implementation. |
| Crawl4AI native MCP | The [self-hosting guide](https://docs.crawl4ai.com/core/self-hosting/) advertises `/mcp/sse` and `/mcp/ws` and tools including multi-URL crawl, JavaScript, screenshots, and PDF. Pi v1.5.2 [supports stdio and Streamable HTTP, and rejects legacy SSE](https://github.com/earendil-works/pi/blob/v1.5.2/packages/coding-agent/docs/mcp.md); WebSocket is not listed. | No direct supported transport at this pinned contract; broad tool exposure also exceeds #147's scope. Do not assume an undocumented `/mcp/http` endpoint. |
| Maintained bridge | [`mcp-remote`](https://github.com/punkpeye/mcp-remote) can bridge a remote SSE endpoint to stdio and filter tools. It adds a separate executable, authentication path, and version to review. Pi already has an extension seam and Crawl4AI has REST. | Do not add a bridge for one page-retrieval call. Revisit only if REST cannot meet the result contract. |

## Proposed adapter contract for #147

Configuration is **off by default**. Enabling requires one explicit base endpoint and a private API token. Use HTTPS for a remote endpoint; HTTP is acceptable only for an explicitly configured loopback endpoint. Never log or publish token, endpoint, or private response. Pify must not install or start the server. The [self-hosting guide](https://docs.crawl4ai.com/core/self-hosting/) describes token authentication; the pinned [server source](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py) returns `status`, `timestamp`, and `version` from the configured health route.

1. Preflight the configured origin with bounded `GET /health`, require `version === "0.9.5"`, then validate the authenticated `POST /crawl` contract. A healthy response alone cannot establish the deployed image identity, configured controls, or page-result shape. The operator supplies separate image/version evidence. [Server source](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py), [security policy](https://github.com/unclecode/crawl4ai/blob/v0.9.5/SECURITY.md).
2. Send exactly one validated `http:` or `https:` URL in `urls`. Do not pass caller-supplied `browser_config`, `crawler_config`, hooks, extraction strategies, `raw:` data, or arbitrary server options. The [route](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py) accepts a URL list and configuration; fixing the request shape in Pify removes those caller powers. Confirm the minimal body against a v0.9.5 fixture before implementation is accepted.
3. Require HTTP success, outer `success: true`, exactly one `results[]` item, inner `success: true`, valid `url`, and nonempty `markdown.raw_markdown`. The outer success alone is insufficient: the [handler can include failed results](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/api.py). The pinned [result model](https://github.com/unclecode/crawl4ai/blob/v0.9.5/crawl4ai/models.py) defines `success`, `url`, optional `redirected_url`, status/error, and serialized `markdown.raw_markdown`.
4. Normalize to `{requestedUrl, finalUrl, retrievedAt, durationMs, text, sha256, extraction, status, reason, citationEligible}`. `requestedUrl` is the submitted URL. `finalUrl` is `redirected_url` when verified, otherwise `url`; if redirect provenance is inconsistent or either URL violates policy, fail closed. `retrievedAt` and `durationMs` are measured by Pify; `sha256` covers the exact retained UTF-8 `text` or excerpt; `extraction` records `crawl4ai-rest`, server `0.9.5`, and `raw_markdown`. These fields are **Pify's proposed record**, not an upstream response claim. [Result model](https://github.com/unclecode/crawl4ai/blob/v0.9.5/crawl4ai/models.py).
5. Use `complete`, `partial`, or `failed` with an explicit reason. Truncation may be `partial` and cite only the retained excerpt when requested/final URLs and extraction remain verified. Missing provenance, failed retrieval, empty text, malformed or oversized response, timeout, or policy rejection is never citation-eligible. A claim's citation must point to this actual page record, never to a URL guessed from generated text. [#38](https://github.com/fnayou/pify/issues/38).

**Initial configurable validation limits:** one URL per call; five pages per research run; one concurrent call; 20 seconds per page; 60 seconds per run; 64 KiB retained UTF-8 text per page. Bound HTTP response bytes separately, abort on excess, and count failed calls toward the run budget. Do not deep crawl. These are [#146's proposed limits](https://github.com/fnayou/pify/issues/146), not claims about Crawl4AI defaults. The server's own [config.yml](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/config.yml) has broader defaults and independent request, page, and wall-clock caps.

## Security ownership

**Pify can enforce:** explicit enable/disable, endpoint allowlist, token handling, URL scheme and domain allow/deny rules on submitted and returned URLs, no local-file transmission, fixed request body, timeout, page/concurrency/text/response budgets, result schema, citation eligibility, and treating page text as untrusted. A Pify check of the first hostname cannot govern what the remote browser fetches after redirects or DNS changes. [#38](https://github.com/fnayou/pify/issues/38), [Crawl4AI result model](https://github.com/unclecode/crawl4ai/blob/v0.9.5/crawl4ai/models.py).

**Operator-controlled server must enforce:** supported patched image, Bearer authentication, access restriction and HTTPS for remote traffic, globally routable destinations at each DNS resolution and redirect, protection for loopback/private/link-local/cloud metadata, and independent network egress rules. Keep `CRAWL4AI_ALLOW_INTERNAL_URLS` and `CRAWL4AI_ALLOW_INSECURE_TLS` off. Crawl4AI v0.9.5's [egress broker](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/egress_broker.py) describes DNS pinning and redirect checks, but [v0.9.3–0.9.5 advisories](https://github.com/unclecode/crawl4ai/blob/v0.9.5/SECURITY.md) show that other fetch paths bypassed earlier controls. Patch level alone is not proof of deployment policy; test and monitor the actual server. Never send a local marker file to prove this boundary. [Security policy](https://github.com/unclecode/crawl4ai/blob/v0.9.5/SECURITY.md).

## Acceptance checks and unresolved risks

- **Mock HTTP, no private service:** off switch makes zero calls; missing endpoint/token refuses; wrong health version refuses; auth header is sent only to configured origin and never logged; exact one-URL body; malformed/failed/oversized/partial results; absent or conflicting redirect provenance; private and metadata destinations; page and run deadlines; five-page and one-call caps; no citations for failed or unprovenanced content. Test public redirects and DNS changes with controlled fixtures. [#146 test contract](https://github.com/fnayou/pify/issues/146).
- **Separately authorized real-instance test:** only after owner approves a specific instance and controlled public test URLs. Verify operator image digest/version and egress settings out of band; then check token rejection, `/health` version plus `/crawl` shape, one public page, a controlled redirect, blocked internal/metadata destinations, timeout, provenance, and no token or private body in public artifacts. Do not infer support from `/health` alone. [Upstream health and crawl routes](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py), [security policy](https://github.com/unclecode/crawl4ai/blob/v0.9.5/SECURITY.md).
- **Open:** Minimal `POST /crawl` body and `markdown.raw_markdown` serialization need fixture proof with the exact v0.9.5 image; actual operator image, egress deployment, final-URL behavior, and live latency remain unverified. No general web-search provider is chosen here. These are implementation gates, not evidence of a released Pify capability. [Server route](https://github.com/unclecode/crawl4ai/blob/v0.9.5/deploy/docker/server.py), [result model](https://github.com/unclecode/crawl4ai/blob/v0.9.5/crawl4ai/models.py).
