# W4-02-S-D: optional SearXNG URL discovery contract

**Status, 2026-11-22:** Discovery for [#167](https://github.com/fnayou/pify/issues/167), supporting [research capability #38](https://github.com/fnayou/pify/issues/38). Pify remains a bootstrap project. This is a source-based proposal, not an implemented or released integration. No private SearXNG or Crawl4AI instance, endpoint, credential, query, or response was contacted or recorded. No candidate integration was installed in Pi.

## Decision

**Conditional go for a narrow native Pi extension calling SearXNG's JSON REST API in #168.** Reuse the separately operated SearXNG search service, not a search engine implementation inside Pify. Add no third-party search runtime package for one bounded URL-discovery operation. This choice must be proved at the isolated Pi 1.5.2 and mock-service seam before implementation can be accepted. The exact version and security settings of the owner's deployed service remain unknown and require separately authorized validation.

The reviewed upstream source snapshot is full SearXNG commit [`c6ee3e9fd0235004a694e63720efc869bb1e3594`](https://github.com/searxng/searxng/commit/c6ee3e9fd0235004a694e63720efc869bb1e3594), matching the 2026-11-21 [documentation build](https://docs.searxng.org/dev/search_api.html). This is an API review pin, not a claim that the owner runs that commit. No GitHub latest-release object was available on 2026-11-22; a deployed version string or container image must be established without exposing the private service. SearXNG's [license](https://github.com/searxng/searxng/blob/c6ee3e9fd0235004a694e63720efc869bb1e3594/LICENSE) is AGPL-3.0-or-later. Pify would neither bundle nor manage the server.

## Upstream API and response

The [SearXNG Search API](https://docs.searxng.org/dev/search_api.html) supports `GET` or form-encoded `POST` on `/` or `/search`. Use `POST /search` with a fixed `application/x-www-form-urlencoded` body containing only the approved `q` and `format=json`, plus any explicitly reviewed filters. POST keeps query text out of the URL, but SearXNG still forwards it to configured external engines. JSON must be enabled in `search.formats`; requesting an unavailable format returns 403. The [installation example](https://docs.searxng.org/admin/installation-searxng.html) enables HTML only, so a browser page working is not JSON-API evidence.

The pinned [JSON serializer](https://github.com/searxng/searxng/blob/c6ee3e9fd0235004a694e63720efc869bb1e3594/searx/webutils.py) supplies `query`, `results`, `answers`, `corrections`, `infoboxes`, `suggestions`, and `unresponsive_engines`. A [result](https://github.com/searxng/searxng/blob/c6ee3e9fd0235004a694e63720efc869bb1e3594/searx/result_types/_base.py) may carry URL, title, content snippet, one or more engines, score, category, and publication date; optional metadata varies by engine. The score is a ranking signal, not verified relevance or factual confidence. Pify should retain only valid ordinary URL results and available metadata. It should not turn `answers`, infoboxes, snippets, or search-ranked URLs into citations.

Normalize the proposed candidate record to `{provider, query, retrievedAt, url, title, snippet, engines, publishedAt, status, warnings}`. This is Pify's contract, not the upstream response shape. `provider` is exactly `searxng`; `status` distinguishes `complete`, `partial`, `empty`, and `failed`. A 200 response with usable results and `unresponsive_engines` is `partial`; empty results with engine failures are `failed` or `degraded`, never a clean `empty`. Missing or malformed `results`, HTML instead of JSON, oversized body, or invalid URL is an explicit failure. Preserve the original engine warnings without treating their text as instructions. Validate candidate URL scheme, credentials, and destination before any later page retrieval.

The [search syntax](https://docs.searxng.org/user/search-syntax.html) includes engine/category bangs and external bangs. Do not assume a query uses only the operator's intended engines. Require exact outbound-query review when local or private context may enter it; reject or explicitly review engine-switching syntax. An operator-controlled SearXNG engine allowlist and egress policy are separate from Pify's client checks. Pify cannot prove which upstream engine actually received a query from the JSON response alone.

The optional [SearXNG limiter](https://docs.searxng.org/admin/searx.limiter) requires Valkey and may block clients; upstream engines can also timeout, CAPTCHA, or rate-limit. Treat HTTP 429 and `Retry-After` as a bounded rate-limit outcome. Do not retry beyond the run budget or fall back to another provider. A 403 may mean JSON disabled or ingress authentication denied; report the ambiguity without probing private settings. Distinguish 5xx, TLS, timeout, non-JSON, malformed JSON, and engine-partial outcomes.

## Proposed security and budget boundary

Pify must keep SearXNG disabled and unconfigured by default. The user explicitly selects `searxng` and one endpoint; no implicit environment discovery, public instance, automatic fallback, or startup request. Use HTTPS with certificate verification for remote endpoints. Allow HTTP only for an explicitly configured loopback origin. Reject URL userinfo and cross-origin redirects; do not forward credentials to a redirected origin. If a reverse proxy needs a token, load it from protected configuration and send it only in a header to the approved origin. The SearXNG `server.secret_key` is not a client API token. Never log the private endpoint, token, query derived from private content, or response body. [Server settings](https://docs.searxng.org/admin/settings/settings_server.html), [search API](https://docs.searxng.org/dev/search_api.html).

Use #38's permission and privacy boundary to review the exact query before network egress when it may contain private local material. If the caller cannot approve interactively, return a structured refusal or approval-required outcome. Pattern matching alone cannot prove a query is safe. Treat the SearXNG response as untrusted; do not execute instructions inside snippets or allow a result URL to bypass #147's URL/egress checks.

**Initial configurable validation limits, not SearXNG defaults:** three queries per research run, five retained candidates per query, one concurrent search, ten seconds per query, 256 KiB HTTP response bytes, and a shared #38 run deadline. Count failures and retries toward the budget. Abort an oversize or slow response while streaming. Page retrieval retains #147's separate page limits. The server operator must independently restrict engines, ingress, request rate, and upstream egress; Pify cannot enforce those after handing a query to SearXNG.

## Acceptance and unresolved proof

- **Mock service, isolated Pi, macOS/Linux:** off or missing configuration makes zero calls; explicit provider and approved query send one bounded form request; malformed endpoint, unsafe redirect, TLS failure, secret leak, query bang, private-content approval failure, invalid candidate URL, duplicate URL, oversized or non-JSON response, clean empty result, partial engine failure, 403, 429, 5xx, timeout, cancellation, and budget stop have clear statuses. No other provider is contacted. Supplied-URL retrieval works when search is absent. This test seam follows [#38](https://github.com/fnayou/pify/issues/38) and [#168](https://github.com/fnayou/pify/issues/168).
- **Separately authorized real-instance check:** first record the deployed version/image and approved engine/JSON configuration privately. With owner authorization, perform one harmless public query through the exact Pi path, validate result and failure metadata, TLS and authentication behavior, and redact endpoint, token, query if sensitive, and response text from public evidence. Do not probe internal targets or contact Crawl4AI as part of this search check. A healthy UI or `/config` response alone does not prove a successful JSON search.
- **Still unverified:** actual deployed version, engine policy, ingress authentication, JSON enablement, private-instance latency, and Pi/Pify behavior of a new adapter. No source pin or current integration is a released Pify capability. #167 should stay open until its source decision and compatibility criteria are reviewed; #168 remains blocked by #167.
